Arquitetura do sistema

Quatro apps Next.js, um backend Convex, uma tesouraria Stellar. Cada app serve um público e vive na própria origem; todos escrevem no mesmo deployment Convex, que é a única fronteira com o mundo externo. Este desenho mostra o que roda hoje em main — o que ainda não existe está tracejado.

Topologia

  • estágio 2 ou ainda não construído
  • domínio anexado e servindo

Um app Auth0 para tudo. Agency e admin compartilham client id e aud; a distinção de equipe é uma conexão com MFA obrigatório, não um segundo app. O Convex não enxerga o aud do token, então os wrappers de staff são a porta de nível 1 ("tem linha em mutavStaff"); movimentos de valor (cover_default) serão autorizados pela assinatura on-chain, nunca pelo wrapper. Cookies são Host-Only — uma sessão nunca vaza entre subdomínios.

Dados

29 tabelas, um schema.

  • Identidade e organização — users, agencies, memberships, mutavStaff, agencyDocuments, claimedDocuments, agencyBankAccounts
  • Carteira de garantias — tenants, leases, guarantees, products, guaranteeHistory, guaranteeDelinquencyNotices, contractApplications
  • Cobrança e liquidação — invoices, payments, providerOrders, anchorAccounts, anchorWebhookEvents, bearerAccessAttempts, stellarIndexState
  • Crédito — tenantCreditReports, creditAnalysisSignals, creditAnalysisAssessments
  • Operação — mutavAuditLog, mutavAuditAnchors, reserveSnapshots, waitlist

Três regras que atravessam tudo.

  • Escopo por imobiliária. Dezesseis tabelas carregam agencyId e todas as leituras escopadas passam por um índice by_agency_*; o wrapper injeta o agencyId, o handler nunca o recebe do cliente.
  • PII: hash sim, envelope ainda não. hashPii alimenta os sidecars subjectHash / cpfHash / documentHash para busca sem expor o documento. encryptPii existe mas não tem chamador: tenants guarda CPF, nome, nascimento, e-mail e telefone em texto claro. lacuna registrada
  • Auditoria imutável. Writes de staff registram via appendStaffAudit; cada entrada carrega prevHash e entryHash, e a raiz diária vai para a Stellar. Por isso o Convex é um deployment só — a cadeia precisa de um único escritor.

Como chega em produção

  1. Um projeto Vercel por app, todos no time mutav; DNS com wildcard * ALIAS, então todo subdomínio já resolve para a Vercel e só falta anexar o domínio ao projeto (fund ainda não foi).
  2. O build do app faz o deploy do Convex. Cada vercel.json roda verify-convex-deploy.sh (a CONVEX_DEPLOY_KEY tem que combinar com VERCEL_ENV) e então convex deploy --cmd. O de agency ainda roda o runner de migrações (hoje no-op) e semeia previews.
  3. Pré-produção: schema muda por wipe + reseed, nunca por migração em lugar. bun run seed limpa só as tabelas de demo — waitlist, auditoria, staff e reserva sobrevivem, e um teste garante isso.
  4. Qualidade em CI: lint, typecheck, test e conventions (greps de regressão + contrato de shell). Previews Convex são apagados quando o PR fecha.

Três coisas que o desenho decide

  • Uma API, quatro origens. Os apps são cascas por público; nenhuma regra de negócio mora neles. Tudo que escreve passa por uma mutation Convex com wrapper, e por isso o log de auditoria consegue ser uma cadeia única. Sem Server Actions.
  • A fronteira externa é o Convex, não o browser. Toda chave, todo token de API e toda chamada de bureau saem de actions Convex; o browser só recebe NEXT_PUBLIC_*. A exceção deliberada é a carteira: assinatura de valor acontece no cliente, com a chave do próprio admin ou investidor.
  • Dependência num sentido só. apps/* → packages/* → @mutav-finance/mutav-stellar. O contrato auditado nunca importa daqui, e nunca recebe uma chave daqui.
